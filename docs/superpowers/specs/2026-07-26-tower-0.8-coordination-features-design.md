# Tower 0.8 — four coordination features

**Date:** 2026-07-26 · **Status:** approved, not yet implemented · **Target release:** 0.8.0

Four independent features, designed together because they touch the same three seams
(`claim_intent`, `complete_task`, the board). Each ships as its own PR with its own tests.

- **F1 — Task diff on the board.** A finished task shows _what it changed_, not just green.
- **F2 — Symbol-precise auto-claim.** The hook claims the symbol, not the whole file.
- **F3 — Collisions-prevented counter.** A real number for the value Tower delivers.
- **F4 — Reroute on hard conflict.** A blocked agent gets somewhere else to go.

---

## Context

Tower 0.7.1 is shipped (npm `tower-mcp@0.7.1`, 18 MCP tools, 254 tests). Two fixes found
by dogfooding are on branch `fix/worker-runner-and-empty-task` and not yet merged; F1
builds directly on the `filesChanged` plumbing added there.

These four came out of using Tower on a real repo from a phone. Each closes a specific
gap between "Tower knows something" and "the human or agent can act on it":

| Gap observed                                                     | Feature |
| ---------------------------------------------------------------- | ------- |
| Board says a task is done; you can't see what it touched         | F1      |
| The hook locks whole files, so same-file agents block each other | F2      |
| No way to say how much Tower actually saved you                  | F3      |
| A hard conflict stops an agent and leaves it with nothing to do  | F4      |

### Non-goals

Explicitly out of scope, consistent with the roadmap in CLAUDE.md: ML conflict
prediction, auto-resolution of conflicts, a cross-repo intent graph, enterprise
policy/SSO/audit, an A2A adapter, and a full repo browser on the board (ISSUES/003 asks
for task-scoped diffs, which is F1 — not a file tree).

## F1 — Task diff on the board (stat only)

### Problem

`filesChanged: 3` tells you something happened; it doesn't tell you _what_. From a phone
that's the difference between trusting a delegated task and re-checking it on a laptop.

### Design

The worker already runs `git diff --cached --numstat` to compute `filesChanged`. Parse
that same output into a per-file stat and carry it through task completion.

```
git diff --cached --numstat
30  2  src/auth.ts        →  [{ file: "src/auth.ts", add: 30, del: 2 }, …]
```

**Protocol** (`packages/shared/src/protocol.ts`):

```ts
export const DiffStatEntry = z.object({
  file: z.string().min(1),
  add: z.number().int().nonnegative(),
  del: z.number().int().nonnegative(),
});
```

Added as an optional `diffStat: z.array(DiffStatEntry).max(20).optional()` on both
`DelegatedTask` and `CompleteTaskInput`, alongside the existing `filesChanged`.

**Cap:** 20 entries, sorted by `add + del` descending, so one sprawling refactor can't
bloat a row or the board payload. When entries are dropped, `filesChanged` still reports
the true total — the board renders "… and N more".

**Binary files** produce `-` in numstat instead of counts; store them as `add: 0, del: 0`
and let `filesChanged` account for them.

**Store** (`packages/server/src/store/sqlite.ts`): one new nullable column
`diffStat TEXT` holding JSON, added via the existing `addColumn()` migration path.
`rowToTask` parses it defensively — a malformed value is treated as absent, never thrown.

**Board** (`packages/server/src/board.ts`): the task chip gains a summary
`3 files · +42 −7`; tapping expands the file list. Reuses the existing amber/green chip
logic — a `filesChanged === 0` task stays amber and shows no diff section.

### Tests

- numstat parser: normal, binary (`-`), renames, empty, >20 files (cap + sort)
- store round-trip: write/read `diffStat`; malformed JSON degrades to absent
- worker: a real commit produces the expected `diffStat`
- service: `diffStat` passes through `complete_task` to the stored task

## F2 — Symbol-precise auto-claim (rescoped after reading the code)

### What already exists

**Auto-claim is already shipped.** `hooks/pretooluse-tower.mjs` derives repo, branch and
agent id, calls `cmdGuard` on every `Edit`/`Write`/`MultiEdit`, creates the claim, blocks
on a hard conflict, and fails open on its own errors. Installing the hook (copying
`.claude/settings.example.json`) is already the opt-in gate. **No new setting is needed,
and none should be added** — a second flag inside an already-opt-in hook is redundant
configuration.

### The actual problem: the claim is file-level, so it over-blocks

The hook always sends `symbols: []` (hooks/pretooluse-tower.mjs:69), which the engine
treats as a whole-file claim. And a whole-file claim is **hard** by definition:

```ts
// packages/server/src/engine/collision.ts:32
if (aWhole || bWhole) return "hard"; // a whole-file claim locks the entire file
```

So with enforcement on today, **two agents editing different functions in the same file
block each other**. The engine already knows that case should be `soft` ("same file,
different symbols → overlapping diffs", collision.ts:34) — the hook just never gives it
the symbols to reach that conclusion. On any shared file the hook is too blunt to leave
on, which is the real adoption ceiling.

### Design

Give the hook the symbols it already should have been sending.

1. **`Edit`/`MultiEdit`** — locate `old_string` in the file, then use the existing
   tree-sitter extractor to find the **enclosing symbol(s)** at that offset. Claim those.
2. **`Write`** — a whole-file rewrite genuinely is file-level. Keep `symbols: []`.
3. **Unsupported language or symbol not found** — fall back to file-level (`symbol: ""`).
   Coarser, but never wrong, and identical to today's behavior.

Derivation lives in the CLI as `deriveSymbolsForEdit(path, content, oldString)` so it is
unit testable without a running hook.

**Behavior change:** same-file/different-symbol edits stop being blocked and become soft
warnings. That is a fix, not a regression — it makes the hook match its documented
design. Hard blocks on the _same_ symbol are unchanged.

**Failure policy unchanged:** derivation errors fall back to file-level; the hook still
fails open on any internal error.

### Tests

- TS/JS/Python: edit inside a function → that symbol claimed, not the whole file
- symbol not found / unknown extension → file-level fallback
- `Write` → stays file-level
- two agents, same file, different functions → **soft**, edit allowed
- two agents, same symbol → still **hard**, still blocked
- derivation throws → falls back, never crashes the hook

## F3 — Collisions-prevented counter (deduped)

### Problem

Tower's whole value is the collisions that _didn't_ happen — currently invisible. A
counter turns an abstract promise into "14 collisions prevented this week."

### Design

Every time `claim_intent` returns a **hard** conflict, record it. Naive counting inflates
on retries (an agent re-claims, a heartbeat re-checks), so dedupe on identity:

```
key = sha1(repo + sorted(agentA, agentB) + file + symbol)
```

New table, insert-or-ignore on the unique key:

```sql
CREATE TABLE IF NOT EXISTS prevented_collisions (
  key TEXT PRIMARY KEY,
  repo TEXT NOT NULL,
  agentA TEXT NOT NULL,
  agentB TEXT NOT NULL,
  file TEXT NOT NULL,
  symbol TEXT NOT NULL,
  firstSeenAt INTEGER NOT NULL
);
```

`INSERT OR IGNORE` makes recording idempotent, so the count is "unique collisions
prevented", not "times we said no". Agent pair is sorted so `(alice,bob)` and
`(bob,alice)` are one collision. `countPrevented(sinceMs?)` supports a rolling window.

Surfaced in `BoardSnapshot` and rendered near the collision panel, plus one line in
`tower status`.

**Privacy:** this is a local count in the user's own SQLite file. Nothing is transmitted
anywhere — Tower still has no telemetry, and the README claim stays true.

### Tests

- same collision recorded twice → count 1
- `(alice,bob)` and `(bob,alice)` on one symbol → count 1
- different symbols between the same pair → count 2
- soft conflicts are not counted
- window filter honors `sinceMs`

## F4 — Reroute on hard conflict (safe subset + next task)

### Problem

Today a hard conflict is a red light: "bob is editing `verify()`." The agent stops with
no next move, and in practice retries or waits. Real air-traffic control reroutes.

### Design

When `claim_intent` detects a hard conflict, the response carries two additions:

```ts
export const ClaimIntentOutput = z.object({
  claimId: z.string(),
  conflicts: z.array(Conflict),
  unreadMessages: z.number().int().nonnegative().optional(),
  /** Present on hard conflict: the part of YOUR request nobody else holds. */
  safe: z.object({ files: z.array(z.string()), symbols: z.array(SymbolRef) }).optional(),
  /** Present on hard conflict: an unblocked task you could pick up instead. */
  suggestedTask: DelegatedTask.nullable().optional(),
});
```

Note `DelegatedTask`, not `Task` — `Task` is the sequencer's candidate shape
(`{id, module, description?}`), while the delegation queue holds `DelegatedTask`.

- **`safe`** — the caller's own requested files/symbols minus everything overlapping an
  active claim. "You can't touch `verify()`, but `login()` and `logout()` are free."
  Computed from data the engine already has; no new queries.
- **`suggestedTask`** — the oldest `open` task addressed to this agent (or `"*"`) whose
  subject isn't covered by an active claim, via the existing `listTasks` query. `null`
  when there's nothing useful to suggest.

Both are **omitted entirely** unless there is a hard conflict, so soft-conflict and
clean-claim responses are byte-identical to 0.7.1. The claim is still created exactly as
it is today — this is advisory routing, not a behavior change.

The MCP tool description gains a line telling the agent to prefer `safe` work or
`suggestedTask` over waiting, so models act on it without the human prompting.

### Tests

- hard conflict → `safe` excludes the held symbol, includes the free ones
- fully-blocked request → `safe` is empty, not undefined
- soft conflict / no conflict → both fields absent
- `suggestedTask` skips tasks blocked by active claims; `null` when none
- existing `claim_intent` tests still pass unchanged (backward compatibility)

## Risks

1. **F2 derivation quality.** Wrong symbols mean wrong claims — and unlike today's
   coarse behavior, a _missed_ symbol could let a real collision through as soft.
   Mitigated by falling back to file-level whenever the enclosing symbol is uncertain, so
   the failure direction stays "block too much" rather than "block too little".
2. **F1 payload growth.** 100 tasks × 20 entries on the board snapshot. The 20-entry cap
   and existing 100-task limit bound it; measure before raising either.
3. **F3 undercounts by design.** Deduping means a genuinely repeated collision on the
   same symbol counts once. That is the honest number — say "unique collisions", not
   "times Tower intervened", wherever it is displayed.
4. **F4 suggestion staleness.** A suggested task can be taken between the response and
   the agent acting on it. Acceptable: `accept_task` is already the atomic gate.

---

## Success criteria

- A completed task on the board shows its changed files with +/− counts on a phone.
- With `autoClaim: true`, an agent that never calls `claim_intent` is still protected.
- The board displays a non-zero, non-inflating count of prevented collisions.
- A hard-conflicted agent receives either safe work or another task in the same response.
- 80% branch coverage held; `npm run lint` and `npm test` green on every PR.
